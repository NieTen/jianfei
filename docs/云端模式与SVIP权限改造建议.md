## 一、建议采用的方向

建议把产品升级为：**官方云账号统一管理，本机先保存，云端增量同步；基础功能免费保留，只有有效 SVIP 可以发起 AI 识图；AI 提供方和密钥由云端管理。**

现有 SwiftUI + FastAPI + SQLite 可以继续使用。当前已经有注册登录、会话轮换、账号隔离、同步冲突、伙伴共享和备份基础，不需要重新做一套系统，也不建议为云端化直接更换语言、引入 ORM、微服务或大型网页框架。

需要重点完成六件事：

1. 把“输入私有服务器地址后开户”改为面向普通用户的官方云注册、登录、找回密码和账号管理。
2. 建立服务端权益系统，统一判定 SVIP、到期时间、撤销状态和 AI 使用额度。
3. 云端版 AI 统一走后台；关闭手机直连、后台失败转直连和本机识别旁路，平台密钥不下发。
4. 在已有挑战分享基础上，补齐标准链接、独立数据共享、期限和撤销管理。
5. 保留本地与云端数据副本，另外建立版本备份和异地恢复能力。
6. 优先处理全量加载、无分页队列和历史数据治理，防止运行时间越长页面越慢。

**建议先做性能治理和云端权限基础，再开放公网使用。** 不能先把现有私有后台直接暴露到公网，之后再补会员控制和滥用限制。

## 二、现状核实：哪些已有，哪些需要补齐

以下结论来自本轮源码阅读；没有读取用户手机数据库，也没有复现真机卡死。

| 能力 | 当前实现 | 云端化缺口 |
| --- | --- | --- |
| 注册与登录 | 用户名密码注册、登录、访问令牌、刷新轮换、恢复码、退出和设备撤销 | 邮箱验证与找回、账号安全页面、公网防滥用、统一云入口 |
| 会话 | 访问令牌 15 分钟，刷新令牌 30 天；后台保存令牌哈希 | 刷新重放处置、全设备退出、找回后的完整生命周期与审计 |
| AI | 本机 Vision、手机直连、后台代发；后台不可达时可自动直连 | 没有 SVIP 权益模型，也没有统一会员授权链 |
| AI 配置 | 服务器默认配置 + 用户个人配置；个人配置可以覆盖默认值 | 平台供应商管理与用户偏好尚未分离 |
| 同步 | 本地记录与 outbox 同事务；幂等、版本冲突、200 条分页、快照恢复 | 云入口适配、迁移流程、大规模读取与维护的边界 |
| 分享 | 已有邀请码、二维码和系统分享，分享的是 bingjian://join 链接 | HTTPS 链接、无 App 落地页、独立于挑战的数据分享 |
| 共享 | 挑战内按成员、数据类型和时间范围授权 | 通用共享中心、统一授权检查、敏感缓存撤销策略 |
| 本地数据 | SQLite 与媒体按 namespace 隔离；可手动加密导出 | 当前目录排除系统备份；未发现自动本地版本备份流程 |
| 云备份 | 配置备份密码后可每日备份、恢复校验、附件复用 | 默认仍在同一 DATA_DIR 下，需要异地副本和空卷恢复演练 |
| 本地日志 | 写入后最多保留 200 条，查询最近 100 条 | 缺少结构化分类、聚合、稳定分页和独立状态刷新 |
| 状态页性能 | 读日志、离线命令、失败项后还调用 AppModel.reload() | 会全量读取业务记录并重建索引；冲突和命令查询无分页 |
| 后台扩容 | 单实例锁、SQLite、本机媒体、进程内任务和限流 | 不能直接把 workers 或副本数调大就认为支持多实例 |

### 对“几十万条连接记录”的判断

用户反馈的卡顿必须处理，但当前源码不支持“本地连接日志会正常累计到几十万条”的结论：

- LocalDatabase.log() 每次写入后裁剪到 200 条，logs() 查询有 LIMIT 100。
- 后台同步日志展示 audit_logs() 也只返回最近 100 条。
- 页面显示的“待同步记录数”是队列数量，不是日志数量；业务记录、冲突和离线操作也是另外的数据。
- 当前真正明确的风险是：SyncStatusView.load() 最后调用 AppModel.reload()，后者调用 allRecords() 全量读取、解码业务记录，重新构建 RecordIndex，再刷新页面状态。

因此，实施时第一步应核对安装版本、具体页面、各表数量、失败原因及耗时。可能是旧版本、业务数据增长、同步长时间失败造成队列积压，或上述全量刷新放大了耗时；**这些现场原因尚待验证，不能只加一个“清空日志”按钮就宣布问题解决。**

## 三、目标结构与产品边界

~~~mermaid

    CB --> OFF[独立位置的备份副本]
~~~

### 模式建议

| 模式 | 用途 | 约束 |
| --- | --- | --- |
| 官方云模式 | 新用户默认入口 | 固定可信 HTTPS 服务；账号、会员和 AI 以官方后台为准 |
| 离线基础模式 | 不登录或临时断网 | 可记体重、饮食、围度等；联网并授权后再同步；不发起 AI |
| 历史私有部署 | 保留已有 NAS 使用与迁移能力 | 数据、凭据、权益缓存独立；不能成为官方云会员绕过入口 |

建议首期云端发行配置关闭本机 AI 和自带密钥直连，但保留已有实现以兼容历史部署。若仍要求同一个发行版本允许任意私有服务器提供 AI，就无法同时对该私有服务器的算力实行可信的官方 SVIP 控制；应另行确认发行策略，不能声称两者天然兼容。

客户端页面开关负责体验，后台决定是否提供官方 AI 服务。被修改的客户端也不能绕过官方后台权限；用户自己运行的服务或自己修改的离线程序，不属于官方后台能够强制控制的范围。

## 四、基础用户与 SVIP 的权限划分

以下为建议默认规则，尚待确认。

| 功能 | 未登录 | 普通账号 | 有效 SVIP |
| --- | --- | --- | --- |
| 手动体重、饮食、围度、趋势 | 本地可用 | 可用 | 可用 |
| HealthKit、Watch 基础记录 | 按设备授权可用 | 可用 | 可用 |
| 本地食物与常用食物录入、已保存营养查看 | 可用 | 可用 | 可用 |
| 本地照片作为记录附件 | 可用 | 可用 | 可用 |
| 云同步与云端恢复 | 登录后使用 | 可用 | 可用 |
| 伙伴、分享与共享 | 登录后使用 | 可用 | 可用 |
| 个人导出、删除、账号管理 | 本地数据操作可用 | 可用 | 可用 |
| 新建、重试、继续执行 AI 识图 | 不可用 | 不可用 | 联网并校验后可用 |
| 云端模型选择 | 隐藏 | 隐藏 | 在允许列表内选择 |
| 设置平台 API 地址、密钥、额度策略 | 不可用 | 不可用 | 不可用，仅管理权限可操作 |

补充规则：

- 普通用户页面隐藏 AI 识别按钮、自动识别选项、模型和连接设置；可以在“我的”保留会员说明，但不要求每次记餐弹出付费提示。
- 拍照或选照片仍可以作为普通附件保存；添加附件后不能隐式发起 AI。
- 到期后保留已经确认保存的食物、营养值和照片，允许查看、编辑、同步和导出；禁止新的模型调用。历史业务数据不能变成会员到期后不可读。
- 外部照片处理同意与会员权限是两个条件。成为 SVIP 不等于同意把照片发送给第三方。
- 服务不可用、权益未知或无法联网核验时，AI 关闭并给出明确状态，基础记录照常使用。
- 管理员身份与会员套餐分开；拥有管理权限不自动等于拥有个人 AI 使用权益。

## 五、注册、登录与账号逻辑如何改

### 5.1 普通用户流程

建议首期采用“邮箱验证 + 密码”，兼容既有用户名登录，不同时增加短信、多个社交登录和复杂企业账号体系。

1. 第一次打开仍可先填写基础档案，也可选择先登录；不再要求普通用户填写 NAS 地址。
2. 注册提交邮箱、密码、称呼；发送验证信息，通过后建立正式云账号。
3. 登录后先确认本机数据归属，再进入同步。
4. 提供忘记密码、修改密码、邮箱变更、设备管理、退出当前设备、退出全部设备、删除账号。
5. 老用户的恢复码继续作为兼容恢复方式；新增邮箱不能未经证明就绑定到旧账号。

手机号和第三方登录是后续可选项。若增加第三方身份，单独建立身份关联表，不能仅凭对方返回了同名邮箱就自动合并两个账号。

### 5.2 后台落点

在现有 AuthService 上增量扩展，不为了“标准化”强行换成 JWT。当前随机令牌 + 哈希落库 + 可撤销会话也能支持云端。

建议新增或补齐：

- 用户已验证邮箱、邮箱验证时间；规范化后的邮箱唯一约束，保留现有 user_id。
- 验证与找回凭证表：用途、用户或待验证地址、凭证摘要、过期时间、使用时间、失败次数。不同用途的凭证不能互用。
- 修改密码后撤销旧会话；找回成功后明确要求重新登录。
- 刷新令牌轮换保留，补充令牌族和重放检测；客户端已有刷新请求合并和上下文版本校验，应保留并覆盖并发回归，避免正常请求把自己误踢下线。
- 对验证码发送、注册、登录、找回分别限制 IP、账号和设备频率。当前 RequestGuard 主要是进程内按 IP 计数，不足以代替完整账号防滥用。
- 清理过期限流桶；配置可信反向代理范围，不能把任意客户端提交的转发头当真实 IP，也不能让全部用户被误识别为同一个代理地址。
- 注册确认隐私与云同步规则，照片备份和外部 AI 处理单独选择。

找回接口应对存在与不存在的账号给出一致提示，凭证单次、短时有效，服务端安全存储，并限制重复发送。这些措施参考 [OWASP 密码找回建议](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)。

### 5.3 账号隔离与本地数据归属

登录、退出、切换账号和更换服务器都必须取消旧同步、旧 AI 任务轮询及旧权益刷新，并阻止迟到结果写回新身份。

本地 namespace、Keychain、权益缓存、分享缓存至少绑定服务器身份和 user_id。不能只按用户名、邮箱或一个全局 isSVIP 布尔值隔离。

首次登录时明确展示“本机已有记录是否导入此账号”，给出数量与日期范围；未确认前保持独立。退出后的默认页面进入独立离线身份，不展示上一账号的健康记录；原账号的未同步数据隔离保留，不能自动塞进下一个账号。

## 六、SVIP 必须贯穿页面、接口、任务执行

### 6.1 服务端权益模型

建议新增独立 EntitlementService，数据库访问仍统一经过 Repository / Database。

权益至少包含：

| 字段 | 含义 |
| --- | --- |
| user_id | 权益所属账号，来自认证身份 |
| entitlement_key | 例如 ai_food_recognition；套餐映射到能力 |
| status | active、expired、revoked 等服务端状态 |
| valid_from / valid_until | 生效与到期时间，由服务端时钟判定 |
| source / source_ref | 人工发放、兑换或后续支付来源及唯一凭据 |
| revision | 权益版本，便于客户端更新和失效处理 |
| revoked_at / reason | 撤销时间与管理原因 |

套餐名称可以是 basic、svip，但业务判断应查询能力，不要在每个页面散写“套餐字符串等于 svip”。多个来源同时授予权益时，应按有效授权记录计算，不让一次撤销误删另一个仍有效的授权。

建议首期用受限管理员命令或管理 API 发放、续期和撤销，记录操作者与原因；不允许普通 App 提交 is_svip 或有效期自行升级。若要商业付费，再接入可信支付凭据和异步通知。

### 6.2 统一判定链

发起识别时依次检查：

1. 会话、账号、设备有效。
2. 当前账号具有有效 ai_food_recognition 权益，未到期或撤销。
3. 照片属于当前用户且与识别上下文匹配。已同步餐次检查归属、版本及删除状态；尚未同步的本地餐次使用受账号约束的任务上下文、照片摘要和本地修订号，应用结果前再检查是否已编辑或删除。
4. 用户明确同意本次所需的外部照片处理；平台 AI 配置可用。
5. 模型、图片数量、体积、超时和输出上限符合服务器策略。
6. 幂等键匹配既有任务，或在事务中占用额度并创建唯一任务。

路由检查后，AIService.create() 和执行任务前仍要校验。排队期间权益到期、被撤销、注销账号，或服务端收到外部处理同意的撤回时，尚未发送给模型的任务停止。营养自动补全是第二次外部请求，也要重新检查授权和取消状态。

当前识别可以通过 temporary 照片上传处理未同步到云端的餐次，应保留“只上传本次识别所需照片”的选择，不为识图强制开启全部记录/照片同步。为临时识别上传增加明确的用途和权限约束；普通附件备份仍走基础权限，不能将所有媒体上传一并锁为 SVIP。

目前请求中的 allow_external 和本机开关不足以让后台感知后续撤回。建议新增服务端同意记录、consent_revision 和撤回接口，任务绑定授权版本；客户端撤回后立即停止新提交，离线时显示待确认，服务端接收后停止尚未发出的请求。不能承诺离线撤回立即终止已在后台排队或已发给第三方的处理。

权限默认拒绝、每次请求检查、对具体资源核验归属的设计，参考 [OWASP 授权建议](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。这里只靠 SwiftUI 隐藏入口不能形成安全边界。

### 6.3 需要覆盖的绕行路径

| 当前入口 | 建议调整 |
| --- | --- |
| AppModel.recognize() 的 device 分支 | 云端发行配置不可进入本机识别 |
| execution == direct | 云端模式拒绝直连，不读取历史个人密钥发请求 |
| URLError 后 allowOutsideLan 回退 | 云端模式停止回退；保留餐次和照片，提示稍后再试 |
| resumePendingRecognition() | 恢复队列前刷新账号与权益；无权限时标记需处理，不无限重试 |
| submitRecognition() | 上传识别所需照片前校验权益与同意；提交时后台再校验 |
| 拍照/选照片自动识别 | 只有确认权益后可触发；普通用户只保存照片 |
| 快捷入口、深链、历史编辑页 | 统一走同一个能力判断和受控业务入口 |
| AI 模型读取、连接测试、配置写入 | 云端版按用户权限与管理权限拆分，不能成为免费外部调用通道 |

当前 /ai/tasks/{task_id} 与 /data/tasks/{task_id} 共用 task handler，转入 AIService.task()。因此不能只拦截以 /ai 开头的 URL：必须检查任务 kind、所有者与操作权限，同时保留普通用户的导出、删除等基础任务。

取消接口也要校验任务种类，不能让 /ai/tasks/{id}/cancel 操作其他种类任务。模型设置读取、连接测试、配置恢复和旧设置同步同样纳入统一策略，防止页面隐藏后仍在后台执行。

建议把“发起/重试 AI”和“管理本人已有任务”分开：到期用户仍可取消自己的未完成任务、读取必要状态；不允许借通用任务接口获取新生成结果或重新发起模型调用。已确认写入餐次的历史营养数据走普通记录接口继续读取。

### 6.4 运行中到期与额度

- 尚未调用提供方：重新验证失败即取消，释放预占额度。
- 请求已发送：取消只能尽力而为，不能保证外部服务不计费；不自动再试或转直连。
- 到期后返回的结果：保留必要任务审计，暂停向客户端交付新的 AI 候选；按有效权益规则决定后续取回，不能偷偷写入餐次。
- 任务超时、进程中断无法确认是否计费：保留现有 unknown 思路，先核对结果，不能无限重复请求。
- 一次用户识别任务最多自动补全一次；对用户如何计次要固定，建议算一次任务，后台分别记录两次提供方成本。
- 新建与重试使用幂等键和事务额度预占，防止并发设备超额、重复点击重复计次；同一键携带不同内容应拒绝。
- 客户端可缓存权益用于显示，但服务端实时判定为准；缓存过期或账号变化立即失效，离线不凭缓存发起云端识别。

建议错误契约继续使用现有 code、message、retryable、details、request_id：

| 场景 | HTTP / code 建议 | 客户端行为 |
| --- | --- | --- |
| 未登录或会话失效 | 401 / AUTH_REQUIRED、AUTH_EXPIRED | 刷新或登录；不无限重试 |
| 非 SVIP、到期、撤销 | 403 / ENTITLEMENT_REQUIRED、ENTITLEMENT_EXPIRED | 隐藏 AI 操作，保留基础记录 |
| 使用额度耗尽 | 429 / AI_QUOTA_EXCEEDED | 告知重置时间，不后台循环重试 |
| 外部处理未同意 | 403 / AI_CONSENT_REQUIRED | 引导明确授权，不代替用户勾选 |
| 服务暂不可用 | 503 / AI_UNAVAILABLE | 稍后手动重试，不转手机直连 |
| 餐次或照片发生变化 | 409 / MEAL_VERSION_CHANGED | 重新确认当前餐次 |

## 七、API 云端配置如何改

“云端配置”建议分成三层，避免把所有内容放进一个对客户端开放的设置对象。

| 层级 | 内容 | 管理者与返回范围 |
| --- | --- | --- |
| 公共 App 配置 | 最低兼容版本、服务状态、可用登录方式、展示信息 | 平台管理；未登录可读取必要字段 |
| 用户能力与偏好 | 本账号权益、可选模型、估算偏好、同意状态、额度摘要 | 权益由后台计算；用户只改允许的偏好 |
| 提供方私密配置 | API 地址、密钥、模型映射、输出限制、超时、开关 | 仅受限管理入口；不向普通 App 返回密钥 |

现有 ProviderService.configuration() 会优先读取用户 ai_settings；尚无个人配置、api_key 为 null 或未提供、接口地址相同时，现有保存流程可能把服务器默认密钥加密复制到个人配置。显式 api_key 为空字符串表示清除，不能与 null 混淆。虽然密钥加密保存且不直接返回明文，但这种“用户配置覆盖平台配置”的模型不适合统一运营。

建议改为：

1. 平台管理 provider_id、允许模型和密钥引用；用户只提交 model_id 或服务档位，后台映射真实配置。
2. 云端禁止普通用户修改供应商 URL、API Key、任意模型、max_tokens 等成本敏感字段，不能只是把输入框藏起来。
3. 配置更新采用版本号。排队任务记录 provider_id 和 config_revision，执行时重新解析密钥，避免把可解密密钥副本长期放入任务数据。
4. 更换供应商或密钥时明确旧任务取消/继续策略；接口地址改变不自动携带旧密钥。
5. 密钥加密保存，加密主密钥与数据库分离管理；日志、导出和错误响应均不得包含密钥。
6. 沿用并加强 ProviderService.validate_destination()，检查 HTTPS、目标地址、重定向与内网访问规则。云端不接受用户任意 URL 代发。
7. 个人历史密钥留在原有身份作用域，切到官方云不会自动上传、复制或使用。
8. 管理端的模型连通性检查单独限流、审计；用户“查看模型列表”优先读取平台维护的目录，不直接不断请求提供方。

继续采用现有 Responses 协议、共享 food_schema.json、营养缺失最多自动补全一次、候选需用户确认的规则。更换配置方式不应改变营养完整性标准。

建议新增 /app/config、/me/entitlements、/me/ai-preferences、受限 /admin/ai/providers 等接口；已有 /capabilities 保留同步握手职责，并增加兼容的权益摘要。具体新增路径在实施时统一确认，不能直接把旧返回结构替换到导致已有客户端无法解码。

## 八、分享与共享要分开设计

### 8.1 分享：一次性把内容或入口发出去

当前已有挑战邀请码、二维码和系统 ShareLink；需要补的是标准化的链接和更完整的内容分享。

建议首期提供：

- 邀请分享：HTTPS Universal Link 打开 App 的邀请预览；未安装时显示最小落地页和安装说明，登录后继续原邀请流程。
- 成果分享：本地生成用户预览过的卡片，通过系统分享面板发送；默认去除精确健康细节、备注和照片。
- 可撤销的在线分享：按需新增随机不可猜测令牌、过期时间、撤销状态和数据范围；服务端仅保存令牌摘要。

邀请码和分享链接不要包含 user_id、邮箱、访问令牌或 API Key。控制访问频率，避免链接预览机器人误消费单次邀请码；真正的接受应在登录后主动确认时完成。

最小网页落地页只用于邀请或查看明确共享的内容，不需要因此新建一个完整业务网页前端。外部截图、已下载卡片无法远程收回；在线链接撤销只阻止后续访问，页面需要如实说明。

### 8.2 共享：持续授予指定账号读取权限

建议复用现有 ChallengeService 的授权思想，增加统一共享中心：

- 指定接收人，不默认对整个小组开放全部健康数据。
- 分别选择体重、饮食摘要、详细餐次、照片、备注等范围。
- 明确历史起点、结束日期、授权到期时间，默认从授权时开始。
- 首期只读共享；协同编辑另立需求，不能隐含授予。
- 授权、修改、撤销使用版本控制与审计，避免两台设备互相覆盖。
- 服务端每次检查用户关系、授权范围、时间和资源归属；不能只在成员列表隐藏某人。
- 照片、缩略图、导出、分享接口复用同一授权策略，避免正文受限而媒体仍可直接访问。
- 共享记录不进入接收人的个人 outbox，不变成其可同步覆盖的“自己记录”。

当前伙伴页面会缓存摘要，缓存有效期可达 24 小时，断网时会显示未到期缓存。这意味着撤销只能立即阻止新的在线读取，无法让对方已经离线保存的数据瞬间消失。

建议敏感共享默认在线查看；如保留离线缓存，采用短租约、独立命名空间和服务端授权版本，联网立即失效。用户端显示“离线副本时间”，不能把离线旧数据当实时共享。

离线提交撤销时显示“等待服务器确认”；只有服务端接受后，后续在线读取才会被拒绝。共享页面一直打开时也要处理授权到期，不能只在再次进入页面时检查。共享只提供查看权限，不意味着接收人可以用自己的会员调用 AI 处理他人的照片。

## 九、本地与云端双副本，以及真正的备份

### 9.1 同步与备份不能混为一谈

同步会把正确修改同步过去，也可能把误删同步过去。因此“手机一份、服务器一份”满足双副本，但不足以抵御误操作、数据库损坏或服务器磁盘故障。

建议形成以下层次：

| 层次 | 作用 | 建议 |
| --- | --- | --- |
| 本地工作数据 | 离线记录、快速读取、待同步保护 | 保存成功首先落本机；云端失败不撤销本机记录 |
| 云端工作数据 | 多设备同步与换机恢复 | 按用户隔离；基础用户也可使用 |
| 本机版本备份 | 本机误删或升级失败后的恢复点 | 有变更时生成一致性快照，初始建议最多保留最近 7 个日版本 |
| 云端版本备份 | 误删、故障与升级回退 | 初始建议每日备份，保留 30 天并验证可恢复 |
| 独立位置副本 | 云主机或主磁盘损坏 | 备份复制到独立存储位置，密钥另行保护，执行空卷恢复 |

这些保留值是初始建议，需结合照片量、容量预算和删除政策确认。本机与其备份一起丢失时仍依赖云端；同一服务器磁盘上的备份也不是异地容灾。

### 9.2 保留现有同步协议

继续使用 change_id 幂等、base_version 冲突检查、删除标记、entity_ledger、instance_id、epoch 和 generation：

1. 本地 records 与 outbox 同事务写入。
2. 联网后按既有权限和同步开关处理命令、记录和媒体。
3. 每批处理 accepted、duplicate、conflict、rejected，不能因 HTTP 200 就清空整批队列。
4. 拉取按游标分页，游标过期恢复一致性快照；不能清空本机未同步记录。
5. 删除账本持续约束导入和恢复，不能用旧备份复活已删除数据。
6. 同一账号异地并发修改继续显示冲突，不依赖手机时间直接“最后写入覆盖一切”。

首次登录建议引导开启基础记录同步，照片单独选择。关闭同步时明确显示“当前仅本机保存”，不能仍宣称本条记录已经有双副本。

照片要单独报告完整性：目前 SyncEngine.uploadPhotos() 只上传 syncPhotos 开启的餐次照片，另一设备通常在查看时才通过 AppModel.photoURL() 下载，并非自动完整下载全部附件。应分别显示“记录已同步、照片待上传、照片未备份、离线附件已备齐”；提供用户可选的完整离线下载。需要包含照片的本机备份应先核对附件清单，缺失时补齐或明确标记不完整，不能静默跳过后宣称完整备份。

### 9.3 备份实施要点

- 当前 LocalDatabase 初始化把 namespace 目录标记为 isExcludedFromBackup；不能假定 iCloud 或系统备份已覆盖这些数据。
- 本机自动备份应采用 SQLite 一致性快照/备份能力；WAL 模式下不能只复制主数据库文件就认为完整。
- 照片备份写入清单、内容摘要和引用关系；复用附件时必须保留仍被有效备份引用的对象。
- 备份文件放在源数据目录之外的明确位置，避免把备份再次打包进去；磁盘不足时保留上一个有效版本。App 沙盒内的本机备份仍可能随卸载丢失，另提供加密导出到用户选择的文件位置。
- iOS 后台任务不保证每天定时运行：前台补做、后台尽力执行，并显示最近成功时间。
- 当前服务端日备份需要 BACKUP_PASSWORD 配置且已到备份时段；未配置时应显示未启用，不能显示“已备份”。
- 恢复先进入隔离临时库，校验格式、摘要、记录数量、附件完整性和所属账号，再由明确恢复流程合并或替换。
- “恢复本机”“导入某账号”“恢复整个云实例”是三种操作，不能共用一个模糊按钮。
- 客户端 LocalArchive 与后台 DataService 的个人导出包，源码设计均使用 BJAR2 加密封装与 manifest/entity/photo/end 帧，未发现这些核心协议明显不一致；仍须完成真实 Swift/Python 双向互导验收。
- 服务端整实例备份虽然同样使用 BJAR2 和 .bjar，内部却是 backup_manifest、backup_file/backup_object 等帧，必须走后台整实例 restore，不能交给手机个人恢复或个人账号导入接口。文件扩展名相同不代表用途相同。
- 备份恢复不应复活旧会话、已撤销共享、过期会员和平台旧配置；按类型恢复并重新核对授权。
- 最新删除账本及撤销信息需要独立、可恢复的保存策略；只有旧数据快照时不能承诺已删除数据不会复活。

当前删除账本回归覆盖“原数据目录仍保留删除日志时恢复旧备份”，不等于已经证明空磁盘、异地恢复也能保留所有后续删除。该场景必须作为云端上线验收项。

## 十、几十万条数据时如何避免卡死

### 10.1 首先拆开四类数据

| 类型 | 例子 | 能否自动裁剪 |
| --- | --- | --- |
| 诊断日志 | 连接失败、同步摘要、耗时 | 可以，按时间、条数、体积限制 |
| 待执行数据 | outbox、commands、未处理冲突、待识别请求 | 不能当日志删除；先成功、明确取消或处理 |
| 同步协议历史 | changes、receipts、游标与幂等记录 | 依赖协议窗口和恢复策略，不能直接按日志规则删除 |
| 真实业务数据 | 体重、饮食、照片、健康摘要 | 根据用户意愿和产品保留规则处理，不能为提速自动删历史 |

清理按钮应明确写“清理诊断日志”，并说明不会取消待同步记录；“取消排队操作”使用独立动作。不能把未同步记录标成成功、删掉之后只让计数变小。

### 10.2 客户端优先修改

1. 新增轻量状态查询：仅查询同步状态、各队列数量、最近错误和最近成功时间。SyncStatusView.load() 不再调用全局 reload()。
2. 日志、失败项、冲突、离线命令各自游标分页，首屏建议 50 条、单页上限 100 条；列表使用稳定 id。
3. 冲突列表只读取必要摘要，进入详情才解码完整本地/远端 payload；避免 N+1 查询和全量 JSON 解码。
4. 界面只保留有限页面，例如最多 500 条已加载明细；保留筛选和继续查询能力，不让无限滚动把全部历史重新装进内存。
5. 加载在 LocalDatabase actor 或独立后台任务完成；取消页面任务和账号切换后丢弃迟到响应。
6. 业务记录列表按日期和类型查询；趋势先按可见日期范围构建索引，按天聚合后绘图。
7. AppModel.reload() 从“每次重读全部记录”逐步改为按变更更新索引；必须保留当前账号和版本校验，不为优化破坏隔离。

当前 SQLite 访问在 LocalDatabase actor 内，RecordIndex 已用 Task.detached 构建。问题不是“所有 SQL 都在主线程同步执行”，而是全量数据读取、解码、内存驻留、重复索引构建，以及状态发布和大量列表更新仍会产生整体压力。把同一份全量读取再包一层异步并不能解决规模问题。

同步恢复也要控制内存：当前 finishSnapshot() 全量读取本地记录并逐条查队列，restoreSnapshot() 在内存保存全部已见 ID。大规模时建议采用临时持久化快照标记、分批处理及受条件保护的 SQL 对账；pendingPhotos() 和命令发送也按批领取。保留未同步修改和中断恢复语义，不能为了缩小内存直接清掉本地库。

### 10.3 日志策略

本地现有 200 条上限可继续作为首期默认，不必把它扩大到几十万条。建议：

- 成功同步只记录一次汇总：推送数、拉取数、耗时；不为每条健康数据写一条成功日志。
- 同一错误按账号、事件类型和错误码聚合，例如显示“网络不可用，重复 35 次”，保留首次与末次时间。
- 记录结构化字段：id、时间、级别、事件码、简短摘要、重复次数、request_id；长错误内容截断。
- 默认只显示警告、失败和重要状态变化；调试日志有单独短期开关。
- 时间、数量和字节上限同时控制；新增结构化日志索引，例如 created_at + id，按实际筛选补充 level。
- 普通连接/同步成功日志不上传为业务记录；必要诊断仅在用户明确导出时生成脱敏文件。
- 清理按批执行；旧库即便异常存在大量日志，也不能在页面打开时一次大 DELETE 或 VACUUM 阻塞使用。

分页采用稳定游标，例如按 created_at、id 倒序，下一页读取小于上一页末条的记录。值使用参数绑定，显式列字段；不能用越来越大的 OFFSET 扫描几十万条。

### 10.4 后台长期增长与同步维护

后台已有 90 天 changes 清理和 minimum_cursor，必须保留“旧客户端转快照恢复”的配套机制。尚需逐类制定策略：

| 数据 | 建议治理方式 |
| --- | --- |
| 普通请求/诊断日志 | 短期保留、聚合、轮转；容器 stdout 也设置体积与文件数量上限 |
| 安全与会员审计 | 独立权限、按期限归档和清理；不记录密码、令牌、照片与完整健康 payload |
| 已完成 AI 任务 | 结果载荷短期保留；计量、幂等与必要审计另存，分开生命周期 |
| 导出文件与临时上传 | 到期删除临时文件，保留必要任务状态，失败后允许重新生成 |
| receipts | 先定义幂等有效窗口和超期重同步协议，再决定归档/压缩；不能直接定期删 |
| changes | 分批清理、推进有效游标下界、支持快照，不影响未同步业务 |
| entity_ledger / deletion_ledger | 保留去重和防复活能力；不套用普通日志清理 |
| 过期会话、验证凭证 | 按失效状态与审计需求定期清理 |

另有两个源码层面的规模风险应纳入验证：

- Repository.find() 默认 limit=10000。部分列表和维护遍历使用默认值，可能出现超过一万条/一万用户后静默截断；应显式分页，不能仅将上限改成无限大。
- max_sequence() 从当前 changes 求最大值；若清理后变化表为空，可能与已经抬高的 minimum_cursor 不一致，导致新快照续传游标再次过期。这是源码推断、尚未复现；应增加测试并评估持久化单调高水位。

另外，周期维护当前每 30 秒运行，删除账本持久化会读取大量账本并合并、重写文件。云端规模增大后应改成增量持久化和有计划的压缩，同时验证崩溃恢复；不能因其名称含“日志”就取消。群晖 Compose 已配置每文件 10 MiB、3 个日志文件的轮转，根目录 Compose 未定义同类配置，新云环境需复用并核实实际日志驱动。

### 10.5 建议性能验收目标

以下是未来验收门槛建议，不是本轮测量结果：

- 在 1 万、10 万、50 万条合成业务记录及大队列场景分别测试。
- 同步状态页首屏只查计数和各类首批明细，不调用 allRecords()；首屏明细总量有明确上限。
- 在约定基线真机上，暖启动进入状态页 P95 目标不超过 500 ms；冷启动单独计量。
- 单页数据从 1 万增长到 50 万时，读取条数和解码条数仍受页大小约束；用查询计划确认关键索引被使用。
- 页面连续进出、滚动与切换账号后内存不持续增长；可将页面额外峰值内存 30 MB 作为初始预算，测量后确认。
- 断网重试使用退避与抖动，只记录聚合状态；观察到稳定上限，而不是每秒堆积队列。
- 不因清理丢失未同步操作、冲突、删除证明或跨设备恢复所需数据。

## 十三、旧数据迁移、兼容与部署

### 13.1 老版本升级

1. 迁移前生成可恢复备份并校验，记录 schema 与协议版本。
2. 新数据库字段有兼容默认值；旧用户默认基础账号，不因存在历史 AI 配置就自动成为 SVIP。
3. 保留旧的手动录入、体重单位、餐次状态、AI 已确认结果和照片。
4. 云端服务先具备完整权限校验，再让新客户端开放入口；旧客户端请求官方 AI 也必须被拦截。
5. 如果必须停止旧客户端的 AI，只限制该能力；能兼容的基础同步继续工作。确实不兼容时提供升级说明，避免只返回泛化连接失败。
6. 新代码回退不能盲目还原旧数据库，否则会丢失迁移后记录、撤销和删除证明；采用兼容迁移或维护窗口恢复，并提前演练。

### 13.2 NAS/离线数据迁到官方云

单独做“迁移向导”，不能把 serverURL 改掉后让原 outbox 直接推到新账号：

- 先确认源身份、目标云账号、待同步数量、照片量与日期范围。
- 对源数据生成个人加密导出包并验证，不能拿 NAS 整实例备份直接导入个人账号；目标环境先在临时区解析、检查格式和冲突。
- 设计来源标识和旧 ID 到新 ID 映射，处理账号范围、实体版本和幂等键；相同用户名不代表相同身份。
- 不迁移登录令牌、API 密钥、官方权益、旧设备授权和挑战共享许可。
- 迁移健康数据时保留 source_id 去重；保留删除语义；处理照片与餐次、AI 证据引用等关联。
- 展示迁移汇总并核对抽样，完成后源 NAS 保留只读副本一段时间；不自动删除原数据。
- 迁移中断可以续传，重复导入不会生成重复记录。

### 13.3 云部署

首期可继续使用 Docker 单实例 FastAPI + SQLite + 持久卷 + Caddy，但要补齐公网 HTTPS、资源和上传限额、磁盘监控、备份异地复制、日志轮转、故障告警及恢复演练。

当前 Runtime.acquire_instance()、进程内 JobRunner、限流状态和本机媒体都绑定单实例。增加多个 workers 或复制容器不能直接解决容量问题。先用目标数据规模与并发量测量；只有明确需要高可用或并发写入扩展时，再单独规划数据库、共享媒体、任务领取和分布式限流的迁移。

首期管理功能优先采用受限 CLI 或最小管理 API，不为发会员和改模型立刻建设完整网页后台。后续需要可视化运营时，再确定具体界面范围。

如果计划通过 App Store 对 AI 等数字功能收费，建议按 StoreKit 购买、服务端验证、交易防重放、到期/退款/撤销通知及恢复购买设计；具体支付入口和地区例外上线前再核对。账号删除也应能在 App 内发起。依据为 [Apple 审核指南 3.1.1、3.1.2 与 5.1.1](https://developer.apple.com/app-store/review/guidelines/)，这不代表本文承诺某种发行方式已满足审核。

## 十四、建议施工顺序与验收

### 阶段 A：先消除卡顿风险

交付：区分计数来源，轻量同步状态接口，冲突/队列分页，日志结构化与容量上限，业务列表按需查询。

验收：1 万至 50 万条合成记录场景、队列积压、断网重试、反复进入页面、账号切换；不得丢失任何待同步数据。先测量再决定是否还需要扩展 RecordIndex 优化。

### 阶段 B：官方云账号与完整 AI 权限链

交付：固定云入口、邮箱验证与找回、权益服务、会员管理、平台 AI 配置、页面与接口及任务执行拦截。

验收：普通账号即使直接调用 HTTP、修改客户端状态或使用旧版本也不能调用官方 AI；有效会员可识别并保存；到期和撤销生效；营养缺失补全规则仍正确。

### 阶段 C：双副本、备份和旧数据迁移

交付：明确同步状态、本机版本备份、云端异地副本、恢复校验、NAS/离线迁移向导。

验收：两设备并发、断网续传、跨账号隔离、旧包导入、完整/增量备份、空卷恢复及删除防复活。该阶段完成前不宣称已具备可靠双备份。

### 阶段 D：标准分享与共享中心

交付：HTTPS 邀请、卡片分享、授权中心、到期与撤销、缓存规则。

验收：无 App/未登录邀请恢复，单次邀请码并发消费，撤销后正文及媒体均拒绝，离线副本边界清楚。

### 阶段 E：按需要接入付费与扩容

交付：若确定商业收费，再做购买、恢复、退款、通知和运营流程；根据真实负载决定容量演进。

验收：重复/乱序通知不重复发放，退款撤权、换账号购买绑定、防跨账号挪用，以及恢复后权益重新核验。

上述阶段可以拆成独立变更，但官方云开放给普通用户之前，账号隔离、服务端 AI 权限、基础备份和公网限制必须已经完成。发布、镜像和安装包仍按用户后续明确授权执行。

### 必须新增的验证场景

| 领域 | 关键场景 |
| --- | --- |
| 账号 | 重复注册、邮箱未验证、找回凭证过期/复用、并发刷新、退出全部设备 |
| 会员 | 未登录、基础、有效、到期、撤销、未来生效、多来源授权 |
| 接口绕过 | 直接调用 AI、修改请求套餐、旧端点、通用任务别名、越权 task_id/media_id |
| AI 执行 | 排队期间到期、发送前撤销、同意撤回的在线/离线边界、补全前复查、进程中断、额度并发、幂等重试 |
| 页面 | 普通用户自动识别不触发、模型页不可进入、深链拦截、旧缓存失效 |
| 数据不丢 | 到期仍能查看/编辑/导出既有 AI 营养；同步失败仍可本地保存 |
| 共享 | 接收者和时间范围、照片/备注单独授权、撤销后多种读取路径一致 |
| 同步 | 游标过期、变化表清空后恢复、幂等回执窗口、超过一万条列表和维护遍历 |
| 备份 | WAL 一致性、缺失附件、错误密钥、磁盘不足、完整/增量备份与空卷恢复 |
| 性能 | 大业务数据、大失败队列、大冲突列表、历史异常日志、索引计划、真机内存与耗时 |
| 业务兼容 | 公斤存储、当天最后测量、缺测不补零、空餐次与未知营养、自定义底栏与 Watch |

现有后台 test_api.py 已有账号隔离、刷新轮换、同步幂等/冲突、快照、共享范围、AI 营养补全和恢复测试，实施时优先扩展这些测试。客户端保留已有录入、凭据、趋势、生命周期及 UI 回归。仅模拟器通过不能替代 iPhone、HealthKit、Watch、真实 AI 和 NAS 联调。

## 十五、确认方案时需要确定的产品选项

本轮不要求现在提供密钥或部署账号。后续确认可以按下表调整范围。

| 决策 | 本文建议默认值 |
