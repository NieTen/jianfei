# 云端全流程验收

2026 年 11 月 19 日，基于 `f72ac6e` 和本轮工作区修改。范围为方案阶段 A 至 D，涵盖记录性能、云账号与 SVIP、双备份和分享共享。SVIP 由管理命令授予或撤销，可指定有效期。阶段 E 的 App Store 订阅、退款与购买恢复属于可选扩展。

使用合成账号、健康记录与 JPEG。后台端口、客户端数据空间和备份目录均为本轮专用。正式 HTTPS 域名待确定，现有工程默认值指向既有局域网地址。本轮构建显式使用隔离测试地址或空值，未连接该局域网、线上服务或个人数据。

## 记录页与冷启动

同步状态页可能面对几十万条队列命令或旧诊断日志，首次打开业务数据库还可能面对几十万条体重记录。两种负载分别造数和计时。

在 Apple M5 Pro、macOS 27.0、Swift 6.4.2 上，以优化构建执行真实 `LocalDatabase` 和 `RecordIndex`。体重查询每页 50 条，每个规模暖读 30 次。冷读取和建索引分别计时。RSS 是外部采样得到的整个测试进程峰值，包含索引更新阶段，不等于单页新增内存。

| 体重记录数 | 状态页本地查询 | 首次历史分页（含索引准备） | 历史分页暖读 P95 | 冷读全部记录 | 首次构建业务索引 | 进程峰值 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 万 | 2.50 ms | 4.88 ms | 0.93 ms | 0.08 s | 0.08 s | 37.7 MiB |
| 10 万 | 2.94 ms | 44.69 ms | 0.98 ms | 0.84 s | 0.83 s | 201.1 MiB |
| 50 万 | 3.54 ms | 261.29 ms | 1.00 ms | 4.32 s | 4.21 s | 955.0 MiB |

50 万条的初次测试中，光建索引就用了 74.11 秒。解码体重会求值默认时间，原实现重复创建毫秒时间格式器。现在复用原格式器并加锁，保留已有时间文本和毫秒舍入规则，另外将全部记录的查询改成逐行解码。在相同数据集上，冷读加索引从 78.46 秒降至 8.54 秒，峰值从 1176.5 MiB 降至 955.0 MiB。单条保存后的增量读取和索引合并耗时约 218 ms。首次打开超大业务库仍需要等待，低内存 iPhone 的启动上限仍需实测。

另用 50 万条待执行命令和 50 万条旧诊断日志运行原生分页检查。首次汇总连同建立索引耗时 192 ms，首批 50 条命令约 0.086 ms。旧日志尚余约 49.98 万条时读取 50 条约 0.172 ms；分批整理到 200 条共 1.10 秒，每次事务最多清理 200 条。完整遍历 50 万条命令耗时 58.0 秒，正常打开页面只读首批。

## iPhone 实际页面

仓库的完整套件在 iPhone 16 Pro 模拟器（iOS 27.2）通过 **112/112** 项（111 项单测、1 项完整页面点击，零跳过），耗时 296.3 秒，导出 72 张 PNG。覆盖首次设置、基础记录、照片选择器、自定义底栏、云账号页面、权益刷新失败和离线撤权恢复等路径。测试已兼容此系统照片选择器的“完成”按钮，模拟器未提供真机文件保护属性。首次点击年龄输入时记录到一条非致命 SwiftUI 布局警告 `Invalid frame dimension`，流程继续完成。

另在 iPhone 17 Pro 模拟器（iOS 27.2，24B8117）安装测试构建，为两个本地空间分别造数。正式复跑的 2 个 XCUITest 全部通过，耗时 45.6 秒，留存 8 张截图。

- 初始空间含 50 万条离线命令、50 万条旧诊断和 1 条业务记录。连续三次从“我的”打开“同步状态”，屏幕均显示离线操作 500000。点击动作返回后，自动化确认计数分别用了 0.60、0.59、0.59 秒。这些数值包含测试查询开销；未测真机帧率。测试结束时业务记录和 50 万条离线命令全在，旧诊断已分批减少到 198400 条，清理期间仍可操作页面。
- 在 App 中创建加密本机版本、打开版本预览、确认导入并看到结果。成果卡片预览只显示日期、餐次数和当天已记体重，未显示原始数值或备注；系统分享面板可打开。本轮没有把卡片发给任何人。
- 第二个空间含 50 万条体重。两次重启 App 到可以访问标签栏的时间约为 20.8 秒和 12.2 秒，均可打开体重历史并看到正确的 75.5 公斤。正式复跑时，宿主采样的该模拟器 App 进程峰值约 1197 MiB，不能据此认定低内存真机会稳定运行。两次测试的文件缓存和系统负载不同。
- 测试查找部分设置入口时，系统可访问性树未返回屏幕上可见的文字，专用验收脚本改用本机文字识别定位后实际点击。页面结果与退出前的 SQLite 数量另行核对，未进行 VoiceOver 真机验收。

## App 与云端联调

独立模拟器运行同一 App 源码，连接仅在本机可用的 HTTPS 云服务。App 通过真实邮箱验证码接口注册，测试 SMTP 收件箱接收邮件。普通账号保存了手动餐次，页面隐藏识图入口。后台管理命令授予 SVIP 后刷新页面可以使用云端 AI，撤销后刷新入口消失。退出后用相同邮箱和密码从页面重新登录。该项界面用例通过，耗时 78.3 秒。

在另一项界面用例中，SVIP 用户在 App 保存当前云端模型的照片处理授权，通过接口核对实际模型和同意状态。从系统相册选中合成餐盘，后台通过 HTTPS 调用 Responses 测试服务进行识别和一次营养补全。App 将结果写入本机餐次草稿，用户滚动到食物明细后点击“保存”，返回首页。只读核对本机 SQLite，最终餐次状态为 `confirmed`，关联 1 张照片，米饭 100 克、120 千卡，蛋白质 3 克、碳水 25 克、脂肪 1 克均已保存。该项用例通过，耗时 27.7 秒。两项云账号专项均独立于仓库的 112 项套件。

另一个普通账号在 App 的“共享中心”创建了仅允许查看当天体重的授权。接收人通过 HTTPS 读到 72.35 公斤，响应没有饮食、餐次、备注或照片字段，直接读取照片返回 403。发送人返回列表打开原授权，点击“撤销共享”并确认，屏幕显示“授权已失效”。接收人随即重新读取摘要和照片，两次均返回 403。首次脚本在创建成功后经历宿主睡眠，测试接收人的旧令牌过期。重新登录同一接收人后，对同一份授权完成互证和撤销，续跑界面用例 1/1 通过（13.0 秒）。接收端本项通过接口核对。

## 实际业务流程

| 流程 | 操作与通过条件 |
| --- | --- |
| 旧库原地升级 | 从 Git 提取云端改造前的 `f4fbc2e`，实际运行旧服务注册账号、保存体重、含未知营养的餐次和照片。保留整个 SQLite 和媒体目录，换用当前源码并启用云模式。旧会话仍可使用，原密码重新登录后用户 ID、世代、记录全文及照片字节均一致。基础账号的 AI 请求被拒，重启后通过 SQLite 完整性检查。 |
| 云账号 | 通过真实 TCP 调用注册登录接口，从仅在本机收件的 TLS SMTP 服务取得验证码。未验证注册、重复用码、错误密码被拒。验证换邮箱、改密、全端退出、找回密码、被撤销设备重新登记和注销；另一个账号的数据保留。 |
| 基础账号与 SVIP | 基础账号能保存体重、餐次和照片，识图、模型设置和识图临时上传被接口拒绝。用后台 CLI 配置平台接口和模型，幂等授予 SVIP。用户同意后执行后台识别任务，模型缺营养时成功补全一次；仍不完整时任务返回失败原因。验证重复提交不重复扣额、额度用尽、撤回同意、撤销权益及自然到期。云端逐次校验权益；页面刷新时重验，展示租约上限为 5 分钟。一次独立旅程收到 5 封测试邮件、4 次 HTTPS Responses 请求。外部模型为协议替身，未评估真实菜品的识别准确度。 |
| 多端同步 | 两个生产 Swift 同步引擎通过真实 HTTP 登录同一账号，分别使用本地 SQLite；第三份本地库登录另一账号。主动停止后台，离线存体重，重新打开库确认仍有待传记录；重启前后验证补传、照片开关、并发修改、选择本机或云端版本、跨端删除和账号隔离。最终三份队列均为空，19 个业务断言通过。 |
| 邀请与共享 | 三个云账号实际创建和预览挑战邀请，预览后邀请码仍可使用。按接收人、日期、体重、餐次、照片和备注分别检查访问权限，等到授权自然到期后重新请求确认拒绝。恢复旧备份后，旧邀请和共享授权仍失效。 |
| 手机迁移与双备份 | 用 10 类记录和一张 235765 字节的合成 JPEG，从 Python 导出个人包，Swift 解密、迁移写入目标 SQLite，本机版本清空后实际恢复，再从恢复后的库导出给 Python 正式导入。核对公斤、未知营养、日期及照片字节；重复导入 10 条均判定相同。 |
| 后台恢复 | 使用实际 CLI 创建备份，保留独立副本及最新删除账本，移除本轮临时源数据目录，恢复到另一空目录。重新登录核对保留的照片字节，验证已删除的记录与账号没有复活，旧会话、邀请码、挑战授权及通用共享均失效。 |
| HTTPS 与浏览器 | 两份部署 Caddyfile 在相同服务名下解析一致。运行 Caddy 和后台，客户端仅信任本次临时 CA，验证健康接口、AASA 与邀请页面；重启两个进程后实例标识一致。独立 Chrome 真实执行邀请脚本，有效片段生成带服务来源的 App 跳转，缺失或无效片段只显示提示。 |

## Docker 部署实测

在隔离的 Linux arm64 虚拟机运行仓库的 Compose 配置和异地备份覆盖配置。实际启动无特权 Docker Engine 29.10.0、Compose 5.8.0、API 和 Caddy。两个测试账号经 HTTPS 保存 3 条记录与 JPEG 并建立只读共享。强制重建容器后，实例、会话、记录和照片一致。生成增量副本后删除一条记录并撤回授权，再移除本次测试的整个应用命名卷，恢复到空卷。剩余 2 条记录及照片保留，删除记录和旧授权均未恢复。容器的内存上限为 512 MiB，CPU 配额为 1 核。容器内的常规回归通过 108 项，显式协议用例按开关跳过；随后在同一镜像中单独启用并通过该项，耗时 132.0 秒，覆盖全部 109 个不同用例。

## 设备编译与保护路径

用 Xcode 27.2 编译通用 iPhone 与 Watch Release 设备目标，验证主程序为 arm64、Watch 包含 arm64 和 arm64_32，测试 HTTPS 地址确实来自构建配置。实际用户域名仍待确定。本轮没有生成 IPA、安装到用户手机、签名分发、推送镜像或提交发布。

Mac 锁屏时，完整文件保护拒绝写入备份清单。修复前连续两次失败留下 2 个没有清单的加密包。修复后使用相同的保护策略和输入，连续两次失败都没有留下无清单的包。

Mac 解锁后，从当前 Swift 产品源码重新编译，在独立测试空间创建备份。归档 `.bjar` 和清单 `.json` 都只有一份，两者的实际文件保护属性均为 `NSFileProtectionComplete`。新建备份服务实例后能读到该版本，密文摘要与清单一致，错误口令被拒绝。随后清空测试库，从该版本恢复 10 类记录和一张合成 JPEG，逐条核对记录 ID、内容与照片字节后，再次导出成功。原始日志位于本机 `build/全流程验收/解锁保护复验/`。

同次解锁复验先运行 7 项备份与迁移专项，全部通过，耗时 3.14 秒。随后用同一测试程序执行包含这 7 项的 macOS 原生套件，**44/44 通过**，耗时 69.06 秒。50 万条离线命令均能分页读回，50 万条旧诊断分批整理到 200 条耗时 1.06 秒。测试前后源码摘要一致。逐项结果见本机 `build/全流程验收/客户端/解锁复跑/`。

iOS 模拟器也通过了 7 项备份与迁移回归，以及从实际页面创建和恢复备份的操作。物理 iPhone 的锁屏、解锁和钥匙串行为仍待真机验证。

## 目标环境边界

本轮覆盖回环 HTTPS、Linux ARM64 容器、模拟器和真实进程故障恢复。已配对的 iOS 17.5.1 手机在本轮设备列表中不可用，方案中基线真机状态页暖启动 P95 不超过 500 ms 的目标仍待测量。正式域名与 Apple 通用链接托管、外部邮箱投递、商业模型识别准确率、真实异地 NAS、物理 iPhone 和 Watch 的 HealthKit、推送、锁屏保护及低内存行为均需在对应目标环境实测。
