# 业务规则与数据契约

本文解释当前实现中不能仅凭字段名字猜测的约定。修改规则时应同时检查客户端和后台，不能只改页面显示。入口见 [代码导读](代码导读.md)。

## 一、记录、单位和日期

### 统一记录封套

客户端 `AppRecord` 与后台 `entities` 的业务内容相对应。Swift 属性使用驼峰，`Codec` 在线路 JSON 中转换为蛇形；不要对已经是 `JSONObject` 的字段再次手工转换命名。

| JSON 字段 | 含义 |
| --- | --- |
| `id` | 记录标识；新建记录通常为小写 UUID |
| `kind` | 记录类型，如 `profile`、`weight`、`meal`、`health_day`、`daily_status` |
| `business_date` | 归属业务日，格式 `YYYY-MM-DD`，不是更新时间 |
| `payload` | 对应类型的字段；客户端模型在 `Models/Records.swift`，后台校验在 `models.py` |
| `source_id` | 来源标识，例如外部健康样本，用于去重；可以为空 |
| `version` | 服务端版本，用于乐观并发控制；本地新记录从 0 开始 |
| `deleted_at` | 删除标记；不能当成“没有这条记录”直接遗忘 |
| `updated_at` | 记录更新时间，不一定是测量/进食时间 |
| `device_id` | 产生变更的设备 |

同步请求使用 `SyncMutation` / 后台 `Mutation`，其中是 `entity_id`、`base_version` 和独立的 `change_id`，不是直接把整个 `AppRecord` 原样提交。`change_id` 用于幂等回执。

### 体重

- `weight_kg`、`corrected_weight_kg` 及健康/同步中的体重统一为公斤。
- 本机显示偏好由 `AppModel.weightUnitPreferenceKey` 保存；公斤、斤、磅换算集中在 `Domain/WeightUnit.swift`。
- 例如存储 70 公斤，选择斤的设备显示 140 斤；不能把 140 存回 `weight_kg`。
- 档案中的旧 `weight_unit` 字段为兼容保留，不能让后续同步覆盖本机偏好。后台旧字段允许值与本机显示选项不是同一份枚举。
- 当天采用最后一次有效测量；隐藏或来源已删除的样本不参与。时间相同时优先手动来源，再按记录标识稳定排序。
- `representative` 旧字段保留兼容，但不再用于决定当天显示哪次测量。
- 重新打开录入页默认带入最近体重；修改日期/测量时刻时清空输入。首页选了历史日期，就记录首页选定日期，而不是强制今天。

对应位置：`WeightEntry`、`WeightUnit`、`EnergyCalculator.weight`、`RecordIndex.representativeWeight`、`AppModel.recordWeight`、`Views/BodyEditors.swift`。

### 日期

时间戳采用可解析的 ISO 8601 字符串；业务日计算应使用档案时区和该流程要求的日界线。`dayStartMinutes` 是业务日开始的分钟偏移，不能简单地用 UTC 日期截断代替。

跟随今天、手动选择日历日期、测量时刻是不同概念。请保留 `AppModel.day/entryDate`、`RecordDate`、`TimeFormat` 中各自的转换规则。修改日期逻辑时对照 `backend/app/domain.py` 并覆盖跨日和夏令时。

## 二、饮食、营养与能量差额

| 概念 | 当前约定 |
| --- | --- |
| `draft` | 草稿，不计入已确认摄入 |
| `confirmed` | 用户确认的餐次，应有食物且份量已确认 |
| `skipped` | 用户明确表示未进食，不可同时含食物 |
| 没有餐次记录 | 尚未记录，不能自动生成 `skipped` |
| 营养值 `null` | 未知，不能无条件替换为 0 |
| 营养值 0 | 明确为零；不能与未知混淆 |

食物使用 `amount / basis_amount × consumed_fraction` 对基础营养值换算。`locked_values` 中的单项最终值优先，不再重复乘份量。AI 返回的本份总热量应与本份重量匹配，不能误当成每 100 克的数值再次放大。

手动快捷记餐允许只填 kcal，三大营养素仍可未知。远程 AI 照片估算则要求给出重量、热量、蛋白质、碳水和脂肪，不能将两种录入方式的完整性要求混为一谈。

没有记录任何餐次时，首页“已记录摄入”可为 0，但这不代表全天完整。身体参数足够时仍可计算截至当前时间的暂估消耗与能量差额。未知食物热量会阻止把差额当作可计算的完整结果；部分已知营养可累计展示，同时保留缺失提示。

当前消耗与全天预测不同。健康静息能量、活动能量、步数回退和基础代谢/活动系数的选择由 `EnergyCalculator.summary` 与后台 `domain.py` 负责，不能叠加重复计算。基础信息不足或选择仅记录模式时不强行给出基础代谢。

## 三、趋势与菜单

- 体重原始点只来自有记录的日期，用圆点和虚线连接；中间缺测不生成虚假点、不补零。
- 7 日移动平均以 7 个自然日为窗口，至少 3 个有效测量日才产生平均值。单个平均值显示菱形，多个平均值单独用实线连接。
- 关闭均线不能同时移除实际体重的虚线。使用 `WeightTrendMarks` 的两个独立序列，不把平均值直接替换原始点数组。
- 摄入趋势只画有相关餐食记录的日期；首页未记餐显示 0 与趋势缺测不是同一个展示规则。
- `MainTabs` 的自定义底栏独立占位。`PersistentTabController` 只装入当前页，缓存其他页面以保留导航状态，同时转发进入/离开事件，使 `.task` 能取消和重新启动。
- 不能用透明度隐藏所有页面替代生命周期，也不能只给旧 `TabView` 加隐藏偏好就假设 iOS 17 不再出现系统底栏。复现路径及检查在 `RecordingFlowUITests.swift`。

## 四、AI 与凭据

### 三条识别路径

本节三条路径仅适用于私有部署。2026 年 11 月 13 日新增的 `cloud` 模式只允许平台网关：普通账号在页面、上传、任务创建/执行/补全和结果读取各层均不可使用 AI；有效 SVIP 仍需单独同意当前提供方处理照片。已保存的历史餐食及基础手动功能不删除。完整契约及配置见 [阶段 A/B 实施记录](云端改造阶段A与B实施记录.md)。

本机模式使用 `OnDeviceRecognizer`，不等于外部模型的完整营养估算。配置模式可由手机 `ResponsesClient` 直连，也可经后台 `AIService` 代发；相关授权开关分别控制。

远程请求使用 `POST /responses`，输入为文本和所选图片，结构化输出使用共享的 `backend/app/resources/food_schema.json`。首次结果缺少必要营养或格式不正确时自动补全一次；仍失败时提示重试/更换模型，不将不完整结果伪装为已完成估算。AI 候选仍需用户确认。

修改接口结构需同时检查 `AI/FoodRecognition.swift`、`AI/ResponsesClient.swift`、后台 `ai.py`、`models.py` 与共享 Schema。这里描述的是本项目实现，不能据此推断任意兼容服务一定支持图像和严格结构化输出。

### 密钥的三个含义

| 场景 | 含义 |
| --- | --- |
| 编辑页面密钥输入框留空、接口未变 | 保留原密钥；读取模型和测试连接也应使用已有凭据 |
| 后台 `PUT /api/v1/ai/settings` 的 `api_key: null` | 保留现有密钥；不能序列化成空字符串代替 |
| 后台 `api_key: ""` 或客户端明确清除操作 | 清除密钥；客户端通过 `clearKey` 和待同步清除标记区分 |
| 接口地址改变 | 重新核对凭据，不向新地址自动发送旧密钥 |
| 后台有密钥、本机无密钥 | 可用后台代发；不能声称手机已有可直连的密钥 |

手机密钥在 `KeychainStore`，普通设置在本地偏好；后台返回 `has_api_key` 而非密钥明文，后台私有配置由 `ProviderService` 加密保存。

“App 允许 HTTP 后台”与“后台允许请求任意 HTTP AI 地址”是两项策略。后台 AI 目标仍由 `ProviderService.validate_destination` 校验，内网地址需要部署允许列表；不要因为局域网连接需求删除此校验。接口或模型变化后可能要求重新确认外部照片处理授权，不能为了方便取消授权步骤。

## 五、存储、同步和删除

客户端数据位于应用支持目录下的 `BingJian/<namespace>/`，内含 SQLite 与媒体。`records` 保存记录，`outbox` 保存待发变更，`commands` 保存待执行命令，`metadata` 保存游标和身份信息，`conflicts` 保存冲突。

启动时登录会话缺失或因重签而不可读，不等于用户主动退出：继续打开当前已选中的本地数据空间，允许离线查看和记录；后台同步等需认证的能力仍要求有效会话。主动退出、切换后台或登录不同账号时，继续按原有规则隔离数据空间，不能把旧账号记录自动关联给新账号。

后台 `DATA_DIR` 下分为 `db`、`media`、`tmp`、`exports`、`backups`、`secrets`。`db/app.sqlite3` 使用 WAL 和事务；`Runtime` 使用文件锁限制同一数据目录的单实例，生产启动 `--workers 1`。现有后台不是可以随意扩多个进程的无状态服务。

| 后台表组 | 用途 |
| --- | --- |
| `users/devices/sessions/bindings` | 身份、设备、会话和本地身份绑定 |
| `entities/changes/receipts/entity_ledger` | 记录、增量日志、幂等回执、实体账本 |
| `snapshots/snapshot_rows` | 稳定分页快照 |
| `media/tasks/ai_settings` | 照片、异步任务和个人 AI 配置 |
| `challenges/members/consents/scores` 等 | 挑战成员、共享许可与评分 |
| `deletion_ledger` 与删除日志文件 | 删除证明及恢复时的删除约束 |

`instance_id` 标识后台实例；`epoch` 标识同步日志世代；`generation` 标识用户数据世代。它们不是可任意清空的“缓存键”。遇到游标过期/日志世代变化可能恢复快照，但实例或用户数据世代变化需要按现有流程处理，不能自动把本机旧数据重新上传。

客户端保存记录及 outbox 在同一事务；同实体待发/失败变更可合并，但正在发送的变更和其回执仍有独立身份。推送逐条处理 `accepted`、`duplicate`、`conflict` 及失败，冲突留给用户处理。每批/每页最大 200 条，具体模型与端点限制以源码为准。

删除通过标记、账本和任务处理。个人数据重置、账号删除、设备撤销、删除一条体重不是同一动作。HealthKit 来源体重的本地删除会隐藏样本，不代表从苹果健康删除源数据。导入或恢复时不能让已删除记录复活。

## 六、接口入口与排查线索

云端新增 `/app/config`、邮箱账号接口、`/me/entitlements`、`/me/ai-consent` 和 `/me/ai-preferences`；管理员通过 CLI 配置平台 AI 和有期限的授权。服务默认 `private`，不自动将旧账号升级成 SVIP。邮箱找回绑定不可变用户 ID；整库云端恢复后授权冻结，需管理员核验重新授予。

iOS 当前构建默认将 `BINGJIAN_CLOUD_SERVER_URL` 设为 `http://192.168.50.229:8000`，仅为这个精确内网地址放行云端 HTTP；其他云端地址继续要求 HTTPS。构建地址升级时先撤销旧连接的会话与异步上下文，再保存新地址，保留当前本地数据空间及绑定，不把旧凭据转发给新服务，也不自动合并或上传旧账号记录。服务端返回 `private` 或无法连接时，云端能力保持不可用，不降级绕过 SVIP 校验。

同步状态与体重历史页面采用本地数据库游标分页，默认每页 50 条、最多 100 条。诊断日志上限为 200 条/14 天，同类诊断 5 分钟内合并；整理只能删除诊断日志，不能为减少显示数量删除业务记录、照片、待发变更、冲突或离线命令。AI 结果确认以事务内实质内容核对防止覆盖，任务元数据变化不等同于用户修改餐次。

HTTP 前缀为 `/api/v1`。主要分组：`/auth/*`、`/records`、`/sync/*`、`/media/*`、`/ai/*`、`/challenges/*`、`/data/*`。完整定义读 `backend/app/api.py`，请求读 `models.py`；运行时 OpenAPI 位于 `/openapi.json`，交互文档位于 `/api/docs`。

注册不要求系统密钥，但仍校验用户名、密码和称呼。连接测试成功只证明服务可达，不代表注册字段合格或登录成功。

常用错误字段为 `code`、`message`、`retryable`，部分响应带 `details` 与 `request_id`。Swift 错误映射见 `Networking/APIErrorResponse.swift`；字段校验需同时展示所有错误，不要统一吞成“连接未完成”。

个人同步、伙伴共享、外部照片处理分别控制；加入伙伴不意味着自动共享所有数据。涉及共享时优先阅读 `ChallengeService` 的授权检查及 `backend/tests/test_api.py` 的对应场景。
