## 2. 记录页面与日志

### 查询与页面

- `LocalDatabase.syncOverview()` 用 SQL 计数，区分待同步变更、失败变更、冲突、离线命令及诊断日志，不把它们统称“连接记录”。
- `diagnosticLogsPage`、`commandsPage`、`failedRecordsPage`、`conflictsPage`、`weightHistoryPage` 使用稳定排序与游标；默认 50 条，硬上限 100 条。
- 同步状态页、体重历史页提供上一页/下一页，不无限追加数组；重复刷新与切换账号丢弃旧异步结果。
- 状态页不调用 `AppModel.reload()`；打开冲突列表不解码全部远端和本地 JSON，进入详情后才加载单条。
- 新增索引在存储 actor 中按需建立，避免在主线程的数据库构造流程中为大表建索引。

主要代码：[LocalDatabase.swift](../ios/BingJian/Data/LocalDatabase.swift)、[SettingsView.swift](../ios/BingJian/Views/SettingsView.swift)、[TrendsView.swift](../ios/BingJian/Views/TrendsView.swift)。

### 日志保留

保留原 `logs` 表，通过增量补列保存级别、事件码、最后出现时间和重复次数。相同诊断在 5 分钟内合并；单条展示消息最多 1024 字符。清理每次事务最多删除 200 条，只操作诊断表。后台批次之间让出 actor，后续进入页面或写日志会继续整理。

**不按数量删除业务记录、照片、待同步 outbox、冲突或离线命令。** 命令取消仍是用户主动操作。异常旧日志会逐步收敛，迁移瞬间不保证已经只有 200 条。

### 性能实测及边界

在 macOS 27.0、Apple M5 Pro 上，以原生产 Swift 数据库源码编译运行 XCTest；合成 50 万条离线命令、50 万条旧日志及 1 万条体重数据。数据不来自真实账号。

| 项目 | 实测 |
| --- | ---: |
| 50 万命令概览，含首次索引准备 | 186.60 ms |
| 首批 50 条命令 | 0.085 ms |
| 第二批 50 条命令 | 0.082 ms |
| 完整遍历 50 万命令、5000 页 | 54.014 s |
| 最慢单页 | 25.129 ms |
| 约 49.98 万旧日志读取 50 条 | 0.194 ms |
| 主动循环分批清理旧日志至 200 条 | 1.414 s |

查询计划使用索引、没有临时排序。命令查询仍是有序索引扫描，越深的页可能检查更长前缀，不承诺每页耗时恒定。表中的清理时间是测试主动循环结果，App 后台还包含批次让步等待。

这些结果证明分页和清理逻辑在本机合成数据下可执行，**不等于 iPhone 页面帧率、内存或闪存性能**。全局 `RecordIndex` 的启动重载仍读取全部业务记录；本轮消除的是打开状态页额外触发全局重载及列表无界读取。若业务记录本身也累积到数十万条，首页/趋势索引仍需另行测量与优化。

## 3. 云端账号与私有部署兼容

后台默认 `DEPLOYMENT_MODE=private`，保留旧 NAS 的用户名注册、个人 AI 配置及原接口协议。`cloud` 模式启用邮箱验证码注册与 SVIP 限制；升级不会自动给旧账号开通会员，也不删除旧账号和记录。

iOS 的 `BingJianCloudServerURL` 来自构建变量 `BINGJIAN_CLOUD_SERVER_URL`。空值保留原私有模式；官方云版本只接受配置的 HTTPS 地址，不能在页面更改官方地址。非空非法配置按云模式关闭 AI，不能悄悄退回直连。未填写正式地址时，云入口明确提示尚未启用，基础离线记录继续可用。

当前连接也通过 `/api/v1/app/config` 确认服务模式。旧私有服务明确返回 404 时兼容旧协议；云模式网络失败不会降级为可自由使用 AI 的私有模式。权益用于页面展示的租约最多 5 分钟，使用服务器时间差和本机单调时钟；前台和长任务会提前刷新，刷新失败关闭 AI。后端每个关键步骤另行校验，客户端缓存不构成授权。

注册和登录默认不合并未绑定离线数据；用户明确开启关联选项后才能绑定匿名空间。绑定失败保留当前本地空间；账号切换以 `localDataContext` 使旧页面和旧任务结果失效。启动先读本机，再刷新云端状态，断网不挡住基础首屏。

网络层另外绑定 `expectedContext`：临时照片初始化、分块上传、创建识别和照片下载必须沿用发起时的身份；退出、换地址或用户/实例/设备/数据代际变化后，旧请求不能改用新账号继续发送。并发 401 共用一次令牌轮换，迟到的旧登录/刷新响应不覆盖新凭据。

| 账号接口（前缀 `/api/v1`） | 行为 |
| --- | --- |
| `GET /app/config` | 匿名读取部署模式与邮箱能力，不含密钥 |
| `POST /auth/email-code` | `register` 或 `reset_password` 验证码申请 |
| `POST /auth/register` | 云模式校验邮箱验证码，返回会话 |
| `POST /auth/login` | 邮箱/原用户名及密码登录 |
| `POST /auth/refresh` | 刷新令牌轮换；重放旧轮换令牌使会话族失效 |
| `GET /me` | 当前账号基本信息 |
| `POST /auth/reset-password` | 验证码找回，撤销旧会话 |
| `POST /me/password` | 校验旧密码后修改，撤销会话 |
| `POST /me/email-code`、`PUT /me/email` | 校验当前密码、验证新邮箱，撤销其他会话 |
| `POST /auth/logout-all` | 撤销该账号全部设备会话 |

验证码默认有效 600 秒，单次使用、限制错误尝试与发送频率；找回凭据绑定不可变用户 ID，防止邮箱转让或注销重注册后串号。已存在/不存在的邮箱使用相同公开受理响应。邮件通过加密持久队列投递，`delivery_status=queued` 代表已入队，不能解读为收件成功；验证码和密码不进入 API 响应或日志。SMTP 失败有限重试，服务重启可恢复未完成队列。

限流同时包含 IP、账号、设备和验证码维度；IP 内存桶有容量上限与过期回收。生产反向代理必须只信任受控代理传入的真实来源地址，避免所有用户落入同一个代理 IP 的限流桶；不可直接信任任意客户端伪造的转发头。

## 4. SVIP 和 AI 的服务端权限链

`EntitlementService` 聚合同一用户多条有效授权；任一有效来源存在即可使用，到期自动失效，撤销一条不误伤其他有效来源。管理员通过受限主机 CLI 授予/撤销，保存来源唯一凭据与审计事件。本轮没有公开自助升级接口、付款页面或支付回调。

| 检查位置 | 云模式要求 |
| --- | --- |
| 页面与 AppModel | 有效会话、已确认的云模式、有效 SVIP；普通账号隐藏识别和模型设置入口 |
| 模型选择 | 只能选平台白名单，不能提交上游 URL/密钥 |
| 临时识别照片上传初始化及分块上传 | 当前 SVIP、同意版本、提供方版本、照片/用户归属 |
| 创建识别任务 | 权益、照片授权、餐次/图片归属、幂等键、可用额度 |
| 排队任务开始及发送给上游前 | 再验权益、用户代际、原设备与会话族、照片、餐次内容和授权版本 |
| 营养补全请求 | 再次鉴权；撤权后不能继续发出第二次外部请求 |
| 任务结果读取 | `/ai/tasks` 与 `/data/tasks` 共用归属和权限检查；失权时隐藏识别结果 |

云端所有识别只经过平台网关。接口/密钥留在服务器；云端 `/ai/settings` 管理入口拒绝用户写入或删除，读取结果脱敏；不允许用户通过旧版 API、临时上传或任务别名绕行。基础照片同步与普通数据任务保持可用。

平台提供方配置变更递增版本，用户必须核对新的照片处理授权。即使管理员声明为内部提供方，也需要明确同意照片处理。用户可在失去 SVIP 后撤回旧授权。网络故障下撤回先阻止本机新请求，并明确提示尚未获得服务器确认；不宣称已收回先前发给提供方的照片。

额度按 UTC 日计算，默认每天 30 次，由 `AI_DAILY_LIMIT` 配置。创建任务在同一事务中预占额度，`user_id + request_key` 唯一，重复请求不重复占额。未发送到提供方即可取消的任务释放预占；请求已发送后超时/失败记为结果不确定，仍占额度，避免误判费用为零。营养缺项仍只自动补全一次。

AI 期间正常同步会增加服务端版本，因此不单凭版本号变化取消任务。服务器核对照片/备注和已存在餐次的实质内容指纹；客户端保存识别结果时，在同一 SQLite 事务内复核原 payload，忽略 `ai_task_id`/`ai_result` 等识别元数据变化。删除或实际编辑会拒绝覆盖，拒绝时记录和 outbox 不变。

## 5. 数据迁移、备份与恢复边界

新增迁移 `003_cloud_accounts.sql`，使用增加字段和表的方式升级。主要增加邮箱、会话族、邮箱挑战/投递队列、授权/审计、平台提供方、用户偏好/同意、AI 额度及临时媒体授权版本。旧用户、口令哈希、会话、记录版本与公斤数值的升级保留已有回归覆盖。生产依赖未新增。

个人“清空数据”保留账号会员和已消费额度，不能靠重置刷次数；注销账号删除邮箱绑定及对应云账号数据。现有删除账本恢复重放同步覆盖新增字段和表。

整库云端恢复额外冻结备份中的授权、保留 `restore_freeze` 审计，失效 AI 同意、邮箱挑战和待发邮件，取消旧识别任务；管理员核实后用新来源凭据授予，再由用户确认照片处理。这样旧备份不会自动复活曾被撤销的 SVIP。私有部署恢复行为保持原有兼容性。**此处只补权限恢复安全边界，没有完成阶段 C 的异地备份、空卷恢复与删除账本独立保护方案。**

## 6. 启用配置与运维入口

用户已确认正式云地址暂未确定，先保留配置项。本轮只实现并测试源码，没有替用户填写正式域名、SMTP 密码或 AI 密钥。未来启用时，需要：

1. 设置后台 `DEPLOYMENT_MODE=cloud`、真实 HTTPS `PUBLIC_URL`、SMTP 参数，参照 [配置模板](../.env.example)。
2. 为 iOS 构建设置 `BINGJIAN_CLOUD_SERVER_URL` 为同一受控 HTTPS 地址。未设置时保持当前私有部署默认行为。
3. 配好生产反向代理、公开可信证书和受控代理来源；仓库根 `Caddyfile` 仍是内网 `tls internal` 模板，不能当作已经部署完成的公网证书配置。
4. 在可信管理终端使用 CLI 配平台 AI 白名单并授予会员。命令从 `backend` 目录运行，使用同一部署的 `DATA_DIR` 与密钥目录。

以下仅为命令模板；没有在真实服务执行。替换所有尖括号参数后使用。密钥由终端隐藏输入，不放在命令行或文档中：

```bash
python -m app.cli ai-configure --url '<Responses服务根地址>' --models '<模型一>,<模型二>' --name '<展示的处理方名称>'
python -m app.cli svip-grant --user '<用户UUID>' --until '<含时区的未来ISO8601时间>' --source manual --reference '<唯一授权凭据>' --reason '<开通原因>'
python -m app.cli svip-revoke '<授权UUID>' --reason '<撤销原因>'
```

同一来源凭据重复开通是幂等操作；已撤销授权不能靠重放原凭据复活。修改平台模型且留空密钥，仅在接口地址不变时复用旧密钥，变更地址必须提供对应新密钥。CLI 的文件系统访问权限应只授予管理员。
