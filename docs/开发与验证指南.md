# 开发与验证指南

本指南的命令面向版本管理中的完整仓库，不依赖历史聊天或本机 `build/` 辅助脚本。项目位置以自己的克隆目录为准；Windows 使用 PowerShell 7。

## 一、开始工作

```powershell
pwsh
git status --short
git log -5 --oneline
```

先阅读 [AGENTS.md](../AGENTS.md)、[代码导读](代码导读.md)、[业务规则与数据契约](业务规则与数据契约.md)，再定位本次需求对应的源码和测试。不要覆盖已有未提交改动。

## 二、Windows 本地运行后台

需要 Python 3.11 或 3.13；CI 覆盖这两个版本。以下从仓库根目录执行，`python` 应指向已安装的受支持解释器。

```powershell
python --version
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
$env:PYTHONUTF8 = '1'
$env:DATA_DIR = Join-Path (Get-Location).Path 'build/本地开发数据'
$env:PUBLIC_URL = 'http://127.0.0.1:8000'
Push-Location backend
try {
    ..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1 --no-access-log
} finally {
    Pop-Location
}
```

已有 `.venv` 时直接使用，不必重建。这个命令将开发数据放在被忽略的 `build/本地开发数据` 下，不连接 NAS 的数据卷。进程持续占用终端，另开 PowerShell 检查：

```powershell
Invoke-RestMethod 'http://127.0.0.1:8000/api/v1/health'
```

接口文档为 `http://127.0.0.1:8000/api/docs`。上例只监听电脑本机；手机联调应另行设置可达的监听地址、端口和防火墙，不能在手机里填写电脑的 `127.0.0.1`。

## 三、测试命令与范围

### 后台

从仓库根目录执行：

```powershell
$env:PYTHONUTF8 = '1'
Push-Location backend
try {
    ..\.venv\Scripts\python.exe -m unittest discover -s tests -v
} finally {
    Pop-Location
}
```

`test_domain.py` 覆盖能量/体重等纯规则；`test_api.py` 覆盖账号、隔离、同步、共享、AI、归档等 API；`test_runtime.py` 启动真实后台进程检查重启和持久化。不要用真实用户密钥或 NAS 数据运行测试。

### iOS 与 Watch

Windows 不能执行原生 Xcode 编译或 XCTest。需要 Mac/Xcode，或现有 GitHub Actions。Mac 上先查看本机模拟器名称/标识：

```bash
xcrun simctl list devices available
xcodebuild -list -project ios/BingJian.xcodeproj
```

将下一条命令的 `模拟器UUID` 换成上一条列出的可用 iPhone 标识：

```bash
xcodebuild -project ios/BingJian.xcodeproj -scheme BingJian \
  -configuration Debug -destination 'platform=iOS Simulator,id=模拟器UUID' \
  -derivedDataPath build/SimulatorData -parallel-testing-enabled NO \
  CODE_SIGNING_ALLOWED=YES CODE_SIGNING_REQUIRED=NO CODE_SIGN_IDENTITY=- \
  CODE_SIGN_STYLE=Manual DEVELOPMENT_TEAM= AD_HOC_CODE_SIGNING_ALLOWED=YES test
```

模拟器也需要正确应用身份和钥匙串授权，不能为了编译方便关闭签名后宣称 AI 密钥保存可用。云端完整命令见 `.github/workflows/ios-test-package.yml`。

| 改动 | 最少应检查 |
| --- | --- |
| 注释/文档 | 差异、链接、路径；源码只改注释时检查非注释语法一致 |
| 体重/能量/日期 | 客户端领域测试，若涉及共同规则再跑后台领域测试 |
| AI/凭据 | 客户端 AI 与凭据回归、受影响的后台 API 回归；真实模型效果另外验证 |
| 底栏/导航 | 生命周期测试、反复切换与导航返回的 UI 流程、相关系统截图 |
| 数据/同步/账号 | 后台 API 和真实进程回归，客户端对应隔离、冲突及恢复流程 |
| 数据库迁移/备份 | 临时数据上的升级与恢复检查，不以清空数据库代替兼容测试 |

## 四、Docker 与群晖

根目录 `compose.yaml` 从源码构建后台，Caddy 提供 HTTPS。已有配置不要覆盖：

```powershell
if (!(Test-Path -LiteralPath '.env')) { Copy-Item -LiteralPath '.env.example' -Destination '.env' }
New-Item -ItemType Directory -Path secrets -Force | Out-Null
# 按 docs/部署与运行.md 填写自己的配置后执行。
docker compose config --quiet
docker compose up -d --build
docker compose exec api python -m app.cli status
```

群晖使用 `deploy/synology/docker-compose.yml`，通过镜像仓库拉取；HTTP/HTTPS 端口和环境变量见 [群晖部署说明](../deploy/synology/群晖部署说明.md)。不要把根目录 Compose 的暴露端口与群晖配置混淆。更新时保留 `.env`、项目名、数据卷和密钥，禁止为排错直接删除数据卷。

## 五、改动与构建注意事项

1. 先确认用户希望修改行为还是只整理代码；本次 AI 接手整理不改变业务行为。
2. 新增 Swift 文件时确认 `ios/BingJian.xcodeproj/project.pbxproj` 的目标成员关系。`tools/generate_xcode_project.py` 会重写工程与部分资源，使用后必须审查全部差异，不能仅创建文件却遗漏编译目标。
3. AI Schema 从 `backend/app/resources/food_schema.json` 共享，不复制出另一套独立定义。
4. 版本分布在手机/Watch 的 Info.plist、Xcode 配置、工程生成脚本及设置页标签；只在需要新版本时同步更新。后台有独立版本，不能因客户端升级就无意义地改后台版本。
5. `.github/workflows/backend-tests.yml` 和 `docker-publish.yml` 会按路径触发后台检查/发布；修改前读当前工作流，避免把源码整理变成部署。
6. iOS 工作流仅手动运行，默认 `create_packages=false`。用户要求打包时才设为 true；`ios17-ui-check.yml` 只验收不打包。
7. 构建时记录源码提交、运行链接、版本/构建号、SHA-256、实际测试结果。不要用旧包链接交付新修复。

## 六、交给其他 AI 的方式

通用 Markdown、UTF-8 源码与标准目录不依赖任何特定 AI 产品。建议把完整仓库交给有代码工作区的 AI，要求先读根目录 `AGENTS.md`；只能上传附件时，可使用本次生成的 `build/AI交接包/`。

- `并肩-AI源码交接包.zip`：保留目录、源代码、测试、配置模板、工程文件与资源，可用于接手开发。
- `并肩-完整源码.txt`：每个文本文件带路径边界，便于全文搜索和上传；不含二进制图片内容，不是可直接编译的单一源码文件。
- `文件清单.json`：列出相对路径、字节数与 SHA-256，区分文本和二进制文件。

不同 AI 的附件和上下文上限不同，不能保证一次读取完整项目。优先给 `AGENTS.md` 和三个导读文档，再按任务补充对应源码与测试；全文合集用于检索，不能替代真实目录中的文件。压缩包仅取版本管理文件，不含 `.git`、`.venv`、真实 `.env`、数据库、照片、签名或构建产物。

可复制给接手 AI 的提示：

> 请先阅读 AGENTS.md、docs/代码导读.md、docs/业务规则与数据契约.md、docs/开发与验证指南.md，再查实际源码和测试。遵守我当前的需求，保留现有架构、功能和数据兼容性。修改前说明调用链和根因，完成后报告实际改动、验证证据及未验证边界。未经我要求不要生成安装包或改变部署。
